# 05 · Структура проєкту та кодогенерація

> **Коли:** старт нового gRPC-проєкту або наведення порядку в існуючому.
> **Результат:** структура каталогів, налаштування кодогенерації, закріплені версії, CI-перевірки.

## Вхідні дані

| Плейсхолдер | Що підставити |
|---|---|
| `{{PROJECT_CONTEXT}}` | Блок з [00](00-project-context.md) |
| `{{OS_LIST}}` | ОС розробників (Linux / macOS / Windows) |
| `{{COMMIT_GENERATED}}` | «комітити згенероване» / «не комітити» / «не знаю» |
| `{{CI_SYSTEM}}` | GitHub Actions / GitLab CI / інше / «немає» |

## Промпт

````markdown
Ти — інженер платформи, що налаштовує gRPC-проєкт.

{{PROJECT_CONTEXT}}

ОС розробників: {{OS_LIST}}
Згенерований код у репозиторії: {{COMMIT_GENERATED}}
CI: {{CI_SYSTEM}}

## Завдання
Запропонуй і опиши структуру проєкту та налаштування кодогенерації.

## Вимоги
1. **Структура каталогів:** де лежать `.proto`, згенерований код, точки входу, внутрішні пакети, тести, скрипти. Обґрунтуй у 1–2 реченнях кожен каталог.
2. **Кодогенерація:** конфігурація для інструмента з контексту (для `buf`: `buf.yaml`, `buf.gen.yaml`, залежності; для `protoc`: готова команда з усіма `-I` та параметрами). Окремо поясни параметри шляхів виводу, щоб шлях імпорту збігався з `go_package`/аналогом.
3. **Версії:** закріпи версії плагінів і runtime-бібліотек. Версію плагіна підбери так, щоб вона відповідала runtime. Актуальні версії та сумісність перевір за офіційною документацією; те, що не вдалось перевірити, познач.
4. **Залежності `.proto`:** як підключити зовнішні (`google/api/annotations.proto`, `google/protobuf/*`): через менеджер залежностей інструмента або вендоринг.
5. **Автоматизація:** `Makefile`/`Taskfile`/скрипти для: встановлення інструментів, генерації, лінтера, перевірки сумісності, тестів. Для Windows запропонуй еквівалент без `make`.
6. **CI:** кроки «лінтер → перевірка сумісності з основною гілкою → генерація → перевірка, що згенерований код актуальний (diff порожній) → тести».
7. **Рішення про комітування згенерованого коду:** подай аргументи за й проти для цього проєкту і рекомендуй варіант.
8. **Перший запуск:** перелік команд від чистого клонування до зеленого тесту.

## Формат відповіді
1. Припущення та питання.
2. Дерево каталогів.
3. Файли конфігурації (повністю).
4. Скрипти/Makefile.
5. CI-конфігурація.
6. Інструкція першого запуску.
7. Рішення, які ШІ не ухвалює сам (комітувати згенероване чи ні; політика версій).

## Не роби
- Не використовуй `latest` для версій плагінів.
- Не додавай інструменти, яких немає в контексті, без пояснення чому.
- Не редагуй згенеровані файли.
````

## Що перевірити людині

- [ ] Чистий клон → команди з п. 6 відповіді → зелена збірка (перевірено запуском).
- [ ] Версії закріплені; плагін відповідає runtime.
- [ ] Генерація ідемпотентна: другий запуск не змінює файли.
- [ ] CI падає, якщо згенерований код застарів чи схема зламала сумісність.
- [ ] Для кожної ОС команди запускаються (особливо Windows).

## Типові помилки ШІ

- Невідповідність версій плагіна й runtime (код не компілюється).
- Параметри шляхів виводу, через які згенеровані файли лягають не туди, де чекає `go_package`.
- Забуті `-I` для зовнішніх `.proto` (`File not found`).
- Плагіни не в `PATH` (`program not found`).
- Рекомендує `latest` або вигадані версії.
