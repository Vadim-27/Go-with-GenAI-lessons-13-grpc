# 17 · Міграція з REST на gRPC

> **Коли:** є REST-API (чи його частина), який треба поступово перевести на gRPC для внутрішнього трафіку.
> **Результат:** відображення ресурсів у сервіси та RPC, чернетка `.proto`, поетапний план з перевіркою еквівалентності.
> Принцип: gRPC виграє всередині між сервісами; REST лишається там, де клієнт браузер або зовнішній інтегратор.

## Вхідні дані

| Плейсхолдер | Що підставити |
|---|---|
| `{{PROJECT_CONTEXT}}` | Блок з [00](00-project-context.md) |
| `{{REST_SPEC}}` | OpenAPI-специфікація або перелік ендпоінтів з прикладами запитів/відповідей |
| `{{TRAFFIC_PROFILE}}` | Хто й наскільки часто викликає кожен ендпоінт; які внутрішні, які зовнішні |
| `{{REST_SEMANTICS}}` | Особливості: коди помилок, пагінація, автентифікація, кеш-заголовки, версіонування |
| `{{MIGRATION_CONSTRAINTS}}` | Терміни, вікна, ризики, команди |

## Промпт

````markdown
Ти — архітектор, що планує поетапну міграцію REST-API на gRPC.

{{PROJECT_CONTEXT}}

## Матеріали
REST-опис:
```
{{REST_SPEC}}
```
Профіль трафіку: {{TRAFFIC_PROFILE}}
Особливості REST: {{REST_SEMANTICS}}
Обмеження міграції: {{MIGRATION_CONSTRAINTS}}

## Завдання
Спроєктуй міграцію.

## Що зробити
1. **Що мігрувати, а що ні.** Для кожного ендпоінту: внутрішній / зовнішній; кандидат на gRPC чи залишити REST (браузер, партнери). Обґрунтуй.
2. **Відображення.** Таблиця: `REST (метод + URL) → сервіс/RPC → патерн → зміни семантики`. Ресурси → повідомлення, колекції → списки з пагінацією, PATCH → часткове оновлення, довгі операції → окремий підхід.
3. **Помилки.** Таблиця «HTTP-статус → код gRPC» для цього API, і що робити з тілами помилок.
4. **Автентифікація й заголовки.** Як переносяться токени, кеш, корелятори.
5. **Чернетка `.proto`** за відображенням; потенційні проблеми (поля, які REST трактував вільно, «мішані» типи).
6. **Поетапний план (strangler):**
   - етап 0: контракт і перевірка еквівалентності відповідей;
   - етап 1: gRPC-сервіс поруч, REST-місток зі схеми для існуючих клієнтів;
   - етап 2: внутрішні клієнти по одному переходять на gRPC напряму;
   - етап 3: порівняння відповідей (тіньовий трафік), метрики помилок і затримки;
   - етап 4: виведення старих REST-обробників, які лишились без споживачів.
   Для кожного етапу: критерії готовності, критерії відкату.
7. **Перевірка еквівалентності.** Як довести, що нова реалізація повертає те саме, що й стара (порівняльні тести на реальних запитах, відмінності допустимі/недопустимі).
8. **Ризики** і як їх зменшити.

## Формат відповіді
1. Припущення та питання (до 5).
2. Що мігрувати (таблиця).
3. Таблиця відображення REST → gRPC.
4. Таблиця статусів HTTP → gRPC.
5. Чернетка `.proto` (потім обов'язкове рев'ю окремо).
6. План за етапами з критеріями готовності та відкату.
7. Тести еквівалентності.
8. Ризики.
9. Рішення, які ШІ не ухвалює сам (межа публічного й внутрішнього, терміни, допустимі відмінності у відповідях).

## Не роби
- Не пропонуй мігрувати все підряд, зокрема публічний браузерний API.
- Не міняй бізнес-поведінку під час міграції без явного рішення.
- Не вигадуй відсутні в специфікації ендпоінти й поля.
````

## Що перевірити людині

- [ ] Публічні/браузерні ендпоінти не потрапили в «мігрувати» без причини.
- [ ] Чернетку `.proto` пройдено через [04](04-proto-review.md).
- [ ] Є тести еквівалентності на реальних (знеособлених) запитах.
- [ ] Кожен етап має критерій відкату, і ви його перевірили.
- [ ] Відмінності у відповідях (формат дати, нульові значення, порядок) свідомо прийняті.

## Типові помилки ШІ

- Мігрує все, зокрема те, що має лишитись REST.
- Не бачить відмінностей: вільні типи в REST, відсутні/null-значення, формат часу.
- Забуває про пагінацію й помилки.
- Пропускає етап перевірки еквівалентності.
- Не передбачає відкату.
