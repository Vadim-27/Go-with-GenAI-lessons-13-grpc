# 09 · Помилки, дедлайни, ідемпотентність

> **Коли:** на етапі проєктування обробки збоїв або при аудиті існуючого сервісу.
> **Результат:** таксономія помилок із кодами та політикою повторів, код мапінгу, політика дедлайнів, ключі ідемпотентності.
> Довідник кодів: [B](B-status-codes-cheatsheet.md).

## Вхідні дані

| Плейсхолдер | Що підставити |
|---|---|
| `{{PROJECT_CONTEXT}}` | Блок з [00](00-project-context.md) |
| `{{RPC_LIST}}` | Список RPC з коротким описом |
| `{{FAILURE_MODES}}` | Відомі збої: що може піти не так у кожному RPC (БД недоступна, дубль, конфлікт тощо) |
| `{{LATENCY_BUDGET}}` | Бюджет часу: загальний SLO, залежності, які викликає сервіс |
| `{{EXISTING_CODE}}` | Існуючий код обробки помилок (або «немає») |

## Промпт

````markdown
Ти — інженер надійності, що проєктує обробку помилок для gRPC-сервісу.

{{PROJECT_CONTEXT}}

## Матеріали
RPC: {{RPC_LIST}}
Відомі збої: {{FAILURE_MODES}}
Бюджет часу: {{LATENCY_BUDGET}}
Існуючий код (якщо є):
```
{{EXISTING_CODE}}
```

## Завдання
Розроби політику помилок, дедлайнів і ідемпотентності та реалізуй її.

## Що зробити
1. **Таксономія.** Таблиця: `доменна помилка | код gRPC | чи повторювати клієнту | повідомлення клієнту | що логувати`. Використовуй точні стандартні коди gRPC; різницю між `InvalidArgument`/`FailedPrecondition`, `Unauthenticated`/`PermissionDenied`, `Unavailable`/`Internal`, `AlreadyExists`/`Aborted` поясни для цього проєкту.
2. **Безпека повідомлень.** Клієнту — корисне повідомлення без внутрішніх деталей (SQL, стек, шляхи). Повна причина — у лог разом з ідентифікатором запиту, ідентифікатор повертається клієнту.
3. **Багаті деталі.** Для машинної обробки додай деталі в стандартний статус (інформація про причину, список некоректних полів, рекомендована затримка повтору) там, де це корисно.
4. **Дедлайни.** Для кожного RPC: значення за замовчуванням, максимум, як сервер передає залишок часу залежностям, і як перевіряє скасування у довгих циклах. Сума дедлайнів залежностей не перевищує дедлайн виклику.
5. **Повтори й ідемпотентність.** Які RPC ідемпотентні й чому. Для неідемпотентних записів — механізм ключа ідемпотентності (формат, час життя, поведінка при повторі з іншим тілом).
6. **Реалізація.** Єдина функція мапінгу «доменна помилка → статус»; приклад використання в обробнику; тести на кожен рядок таксономії.

## Формат відповіді
1. Припущення та питання (до 5).
2. Таксономія (таблиця).
3. Політика дедлайнів (таблиця).
4. Політика ідемпотентності.
5. Код мапінгу і приклад використання.
6. Тести.
7. Рішення, які ШІ не ухвалює сам (відповідність кодів реальним збоям; які операції ідемпотентні; значення дедлайнів).

## Не роби
- Не повертай `Unknown` і `Internal` «про всяк випадок» там, де є точніший код.
- Не показуй клієнту внутрішні повідомлення помилок.
- Не пропонуй повтори для неідемпотентних операцій без ключа ідемпотентності.
````

## Що перевірити людині

- [ ] Кожен рядок таксономії покритий тестом `status.Code(err) == очікуваний`.
- [ ] Повідомлення в відповіді не розкривають внутрішніх деталей (перегляньте реальні відповіді).
- [ ] Коди відповідають реальним збоям вашої системи, а не загальним уявленням.
- [ ] Список ідемпотентних операцій підтвердили ви.
- [ ] Дедлайни залежностей укладаються в загальний бюджет.

## Типові помилки ШІ

- Усе зводить до `Internal`/`Unknown`.
- Плутає `InvalidArgument` та `FailedPrecondition`; `Unauthenticated` та `PermissionDenied`.
- Показує клієнту текст внутрішньої помилки.
- Рекомендує повтори для операцій, що створюють дублі.
- Не пов'язує дедлайн виклику з дедлайнами залежностей.
