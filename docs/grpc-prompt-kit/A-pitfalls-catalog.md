# A · Каталог пасток

> Найчастіші помилки в gRPC-проєктах і в коді від ШІ, разом зі способом їх виявити. Частину пасток зафіксовано на практиці під час створення демо до Уроку 13, решта — відомі антипатерни.
> Дописуйте сюди нові випадки. Використовуйте розділ як чекліст у [18 · Рев'ю PR](18-pr-review-checklist.md).

## Контракт і сумісність

| # | Пастка | Чим небезпечна | Як виявити |
|---|---|---|---|
| 1 | Перенумерація або повторне використання номера поля | Мовчки ламає старих клієнтів на дроті | `buf breaking`; перегляд diff `.proto` |
| 2 | Enum без нульового `*_UNSPECIFIED` або з небезпечним нульовим значенням | Невстановлене значення стає «валідним» | `buf lint`; читання `.proto` |
| 3 | Доменна сутність як запит/відповідь | Запит і відповідь не можуть еволюціонувати окремо | Рев'ю: `rpc X(Entity) returns (Entity)` |
| 4 | `float` для грошей | Помилки округлення | Пошук `float`/`double` у полях грошей |
| 5 | Видалення поля без `reserved` | Майбутнє повторне використання номера | `buf breaking` |
| 6 | Зміна режиму стрімінгу існуючого RPC (unary → stream) | Це зламає всіх клієнтів | `buf breaking` |
| 7 | Плутанина «безпечно перейменувати» | Бінарний формат не зміниться, а JSON (gateway) і згенерований код зламаються | Перевірити, чи є REST/JSON-клієнти |
| 8 | ШІ згенерував `proto2`-ідіоми чи змішав версії | Несумісність із рештою проєкту | Перевірка `syntax = "proto3"` |

## Помилки та дедлайни

| # | Пастка | Чим небезпечна | Як виявити |
|---|---|---|---|
| 9 | Повернення `errors.New(...)`/`fmt.Errorf` з обробника | Клієнт бачить `Unknown`, не може обрати логіку | `grep` по обробниках; тест на `status.Code(err)` |
| 10 | Витік внутрішніх деталей у повідомленні помилки | Розкриття інфраструктури | Рев'ю повідомлень; негативні тести |
| 11 | Немає дедлайну на клієнті | Виклики висять, вичерпуються горутини/з'єднання | `grep` по клієнтських викликах без `WithTimeout` |
| 12 | Ретраї неідемпотентних записів | Дублювання операцій | Рев'ю ретрай-політики; ключі ідемпотентності |
| 13 | Плутанина `Unavailable` і `Internal` | Клієнти не ретраять, коли треба, або ретраять, коли ні | Таблиця з [B](B-status-codes-cheatsheet.md) |

## Стрімінг

| # | Пастка | Чим небезпечна | Як виявити |
|---|---|---|---|
| 14 | Фоновий контекст замість контексту потоку | Ігнорується скасування клієнтом; витік горутин | `grep` по стрімінгових обробниках; тест на скасування |
| 15 | Підписка/таймер не звільняються при виході | Витік пам'яті та горутин при кожному відключенні | Тест із лічильником підписок (див. [13](13-testing.md)) |
| 16 | Конкурентний `Send` з кількох горутин | Гонки, пошкодження потоку | `go test -race`; рев'ю |
| 17 | Обробка `EOF` як помилки | Хибні помилки в логах і метриках | Рев'ю циклу `Recv` |
| 18 | Стрім без обмеження часу життя і без heartbeat | Потоки «висять» через проксі та NAT | Рев'ю політики keepalive/макс. тривалості |
| 19 | Повільний споживач блокує сервер | Одна повільна підписка затримує всіх | Рев'ю політики (відкинути/відключити/блокувати) — рішення людини |
| 20 | Graceful stop зависає на відкритих стрімах | Сервер не завершується | Тест зупинки; таймаут із примусовою зупинкою |

## Безпека

| # | Пастка | Чим небезпечна | Як виявити |
|---|---|---|---|
| 21 | Інтерсептор автентифікації лише для unary | Стрімінгові RPC лишаються без захисту | Тест: стрімінговий виклик без токена має бути відхилений |
| 22 | TLS є, а вимога клієнтського сертифіката відсутня | Це не mTLS: будь-який клієнт підключається | Тест: підключення без клієнтського сертифіката має провалитись |
| 23 | Негативний тест mTLS не доходить до перевірки ланцюжка довіри | Go-клієнт мовчки не надсилає сертифікат, виданий невідомим CA, тож перевіряється лише «сертифіката немає» | Лог сервера має містити `unknown authority`, а не лише `didn't provide a certificate` |
| 24 | Політика доступу «дозволено, якщо немає правила» | Новий метод автоматично відкритий | Тест: метод без правила → `PermissionDenied` |
| 25 | JWT без перевірки алгоритму, `exp`, `aud`/`iss` | Підробка токена (`alg=none`) | Тести на `alg=none`, протермінований, чужий підпис |
| 26 | Токен у логах або в тексті помилки | Витік облікових даних | `grep` по логах; рев'ю логування |
| 27 | Токен по відкритому каналу | Перехоплення | Облікові дані per-RPC мають вимагати TLS поза локальним демо |
| 28 | Reflection увімкнено в продакшені | Розкриває весь API | Конфігурація; прапорець |
| 29 | Демо-сертифікати/секрети в репозиторії | Компрометація | `.gitignore`, сканер секретів |
| 30 | Плутанина рівнів: mTLS = користувач | mTLS ідентифікує сервіс, а не людину | Модель загроз з [11](11-security-auth-mtls.md) |

## Експлуатація та продуктивність

| # | Пастка | Чим небезпечна | Як виявити |
|---|---|---|---|
| 31 | L4-балансувальник прив'язує довге HTTP/2-з'єднання до одного інстанса | Нерівномірне навантаження, нові поди «порожні» | Метрики запитів по інстансах; рішення: клієнтський LB, L7-проксі, `MaxConnectionAge` |
| 32 | Нове з'єднання на кожен виклик | Витрата на рукостискання, вичерпання портів | Рев'ю клієнтського коду |
| 33 | Типовий ліміт розміру повідомлення (4 МБ на приймання) | Падіння на великих відповідях | Тест із великим повідомленням; стрімінг для великих даних |
| 34 | Використання застарілих API (`grpc.Dial`, `WithBlock`) | Поведінка змінюється між версіями | Рев'ю; лінтер deprecated |
| 35 | Версія плагіна кодогенерації не відповідає версії runtime | Код не компілюється або працює некоректно | Фіксація версій; CI-збірка |
| 36 | Відсутній health-check | Оркестратор не знає про стан | Наявність `grpc.health.v1` |

## Бенчмарки

| # | Пастка | Чим небезпечна | Як виявити |
|---|---|---|---|
| 37 | HTTP-відповідь не вичитано й не закрито | З'єднання не повертається в пул, REST «повільніший» штучно | Рев'ю: `io.Copy(io.Discard, ...)` + `Close` |
| 38 | Ліміт з'єднань за замовчуванням у HTTP-клієнті | Спотворює паралельний тест | Налаштування `MaxIdleConnsPerHost` |
| 39 | Занадто мало ітерацій, не враховано розігрів | Нестабільні цифри | Збільшити `-benchtime`, повторити, порівняти `benchstat` |
| 40 | Висновок «gRPC завжди швидший» | Для крихітного повідомлення на loopback транспорт часто домінує; формат виграє, але виклик може бути не швидшим | Міряти власний сценарій; описувати результат як є |
