# 10 · Інтерсептори (middleware)

> **Коли:** потрібні наскрізні можливості: recovery, логування, метрики, трасування, автентифікація, ліміти.
> **Результат:** ланцюжок інтерсепторів для unary **і** стрімінгових викликів із обґрунтованим порядком і тестами.

## Вхідні дані

| Плейсхолдер | Що підставити |
|---|---|
| `{{PROJECT_CONTEXT}}` | Блок з [00](00-project-context.md) |
| `{{CAPABILITIES}}` | Які можливості потрібні: recovery, логування, метрики, трасування, автентифікація, авторизація, ліміти, валідація |
| `{{OBSERVABILITY_STACK}}` | Стек спостережуваності: логер, метрики (напр. Prometheus), трасування (напр. OpenTelemetry) |
| `{{SENSITIVE_FIELDS}}` | Що не можна логувати (токени, персональні дані, поля повідомлень) |
| `{{PUBLIC_METHODS}}` | Методи без автентифікації (health, інше) або «немає» |

## Промпт

````markdown
Ти — інженер платформи, що будує middleware для gRPC.

{{PROJECT_CONTEXT}}

## Матеріали
Потрібні можливості: {{CAPABILITIES}}
Стек спостережуваності: {{OBSERVABILITY_STACK}}
Чутливі дані: {{SENSITIVE_FIELDS}}
Публічні методи: {{PUBLIC_METHODS}}

## Завдання
Спроєктуй і реалізуй ланцюжок інтерсепторів для сервера (за потреби й клієнта).

## Вимоги
1. **Окремі інтерсептори** для кожної можливості, не один монолітний.
2. **Unary і stream.** Для кожної можливості реалізуй обидві версії. Інтерсептор лише для unary залишає стрімінгові RPC без захисту й спостереження.
3. **Порядок.** Запропонуй порядок і поясни його: recovery зовні (щоб ловити паніку наступних шарів); логування/метрики зовні від автентифікації (щоб відмови теж потрапляли в журнал); автентифікація до авторизації й валідації; трасування якнайраніше.
4. **Обгортка потоку.** Якщо інтерсептор змінює контекст (наприклад, кладе дані користувача), у stream-версії обгорни потік і перевизнач метод отримання контексту.
5. **Паніка.** Recovery перетворює паніку на `Internal`, логує стек із ідентифікатором запиту, не показує клієнту деталей.
6. **Логування.** Метод, код, тривалість, ідентифікатор запиту, адреса клієнта. Ніколи: токени, чутливі поля, повні тіла повідомлень.
7. **Метрики.** Лічильники й гістограми за методом і кодом, кількість активних потоків; кардинальність міток обмежена.
8. **Ідентифікатор запиту.** Приймай з metadata або генеруй; передавай далі й повертай у відповіді.
9. **Публічні методи.** Явний білий список; усе інше за замовчуванням захищене.
10. **Ліміти** (якщо потрібні): обмеження швидкості за ідентичністю; код `ResourceExhausted`.

## Формат відповіді
1. Припущення та питання (до 5).
2. Діаграма порядку інтерсепторів і пояснення.
3. Код інтерсепторів (unary і stream) та підключення до сервера.
4. Тести: паніка → `Internal` без витоку; відмова автентифікації потрапляє в лог/метрики; stream-версія працює; токен не з'являється в логах.
5. Що перевірено запуском, а що ні.
6. Рішення, які ШІ не ухвалює сам (порядок у вашому проєкті, ліміти, що вважати чутливим).

## Не роби
- Не логуй вміст повідомлень «для налагодження» без маскування.
- Не пропускай stream-версії.
- Не використовуй застарілі способи підключення трасування; перевір актуальний у документації бібліотеки.
````

## Що перевірити людині

- [ ] Стрімінговий виклик без токена відхиляється (див. [A #21](A-pitfalls-catalog.md)).
- [ ] Паніка в обробнику не валить процес і не розкриває стек клієнту.
- [ ] У логах немає токенів (перегляньте реальний лог після негативних тестів).
- [ ] Відмови автентифікації видно в логах і метриках.
- [ ] Метрики не мають мітки з необмеженою кардинальністю (наприклад, id користувача).

## Типові помилки ШІ

- Лише unary-інтерсептори; стріми лишаються без захисту.
- Невдалий порядок: логування всередині автентифікації; відмови не видно.
- Забуває перевизначити контекст у обгортці потоку: дані користувача не доходять до обробника.
- Логує повні запити з токенами та персональними даними.
- Мітки метрик із id користувача чи шляхом із параметрами.
