````markdown
## README — вимоги
1. **Зміст і що всередині:** дерево каталогів з поясненням, відповідність частин коду ключовим концепціям.
2. **Вимоги до середовища:** таблиця «інструмент / обов'язково? / навіщо / як встановити» для кожної ОС зі списку.
3. **Швидкий старт:** мінімальна послідовність команд від чистого клону до першого успішного виклику, з очікуваним виводом.
4. **Сценарії:** для кожного RPC (і кожного патерну) — команда клієнта, `grpcurl`-приклад (за схемою `.proto`) і очікуваний результат; негативні сценарії (помилки з кодами). Окремо — безпека (токени, mTLS), якщо є.
5. **Тести й бенчмарки:** як запустити й що вважати успіхом.
6. **Типові проблеми:** таблиця `симптом | причина | рішення` (порт зайнятий, не знайдено плагін, відсутні залежності, помилки сертифікатів, несумісність версій).
7. **Нотатки для різних ОС** (особливості оболонки, лапки в JSON, псевдоніми команд).
8. **Відомі відмінності від еталону/слайдів/специфікації,** якщо є.
9. **Що перевірено автором:** на яких ОС і версіях запускалось, що не перевірено.

## Runbook — вимоги
1. Короткий опис сервісу, залежності, критичні шляхи.
2. Дашборди й ключові метрики (за методом і кодом gRPC, затримка, активні потоки).
3. Типові інциденти: сплеск `Unavailable`, сплеск `DeadlineExceeded`, зростання кількості потоків/горутин, нерівномірне навантаження між інстансами, протермінований сертифікат, масові `Unauthenticated`. Для кожного: симптом, як діагностувати, швидка міра, причина, довгострокове виправлення.
4. Процедури: розгортання, відкат, ротація сертифікатів і секретів, збільшення лімітів.
5. Контакти й ескалація (місце для заповнення).

## Правила достовірності
- Кожна команда має бути виконана; якщо ти не можеш її виконати, познач «не перевірено» і не вигадуй очікуваний вивід.
- Не вигадуй прапорці, змінні середовища й шляхи; бери їх із наданих матеріалів.
- Не копіюй зайвих пояснень; пиши так, щоб читач із зазначеної аудиторії зробив крок без здогадок.

## Формат відповіді
1. Припущення та питання (до 5).
2. README (повністю).
3. Runbook (повністю).
4. Перелік команд, які ти виконав, і тих, що лишилися неперевіреними.
5. Рішення, які ШІ не ухвалює сам (пороги алертів, процес ескалації, власники).

## Не роби
- Не вигадуй команди, прапорці, змінні середовища, шляхи та очікуваний вивід.
- Не описуй лише одну ОС, якщо в списку їх кілька.
- Не пиши runbook без прив'язки до метрик і алертів цього сервісу.
````

## Що перевірити людині

- [ ] Нова людина (або ви на чистій машині) пройшла «Швидкий старт» від початку до кінця без допомоги.
- [ ] Очікуваний вивід у документі збігається з реальним.
- [ ] Прапорці, змінні та шляхи існують у проєкті (`grep`).
- [ ] Таблиця проблем містить помилки, які справді виникали.
- [ ] Runbook перевірено хоча б одним навчанням (імітація інциденту) або прочитано власником сервісу.

## Типові помилки ШІ

- Вигадані прапорці, змінні середовища, шляхи.
- Вигаданий очікуваний вивід команд, які не запускались.
- Інструкція лише для однієї ОС.
- Загальний runbook без прив'язки до метрик сервісу.
- Пропущені негативні сценарії.
