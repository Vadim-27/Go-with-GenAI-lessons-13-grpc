# 16 · Зміна схеми без поломок

> **Коли:** треба змінити контракт, який уже використовують клієнти.
> **Результат:** класифікація зміни, безпечний шлях міграції, порядок розгортання, тести сумісності.

## Вхідні дані

| Плейсхолдер | Що підставити |
|---|---|
| `{{PROJECT_CONTEXT}}` | Блок з [00](00-project-context.md) |
| `{{PROTO_CURRENT}}` | Поточний `.proto` (в експлуатації) |
| `{{DESIRED_CHANGE}}` | Що потрібно змінити й навіщо (бізнес-причина) |
| `{{CLIENT_LANDSCAPE}}` | Хто використовує: кількість клієнтів, чи керуєте ви їхніми релізами, чи є JSON/REST-клієнти, чи є збережені повідомлення (черги, файли) |
| `{{ROLLOUT_CONSTRAINTS}}` | Обмеження розгортання: чи можна зупинити, чи співіснують версії, вікно змін |

## Промпт

````markdown
Ти — архітектор API, що відповідає за сумісність контрактів.

{{PROJECT_CONTEXT}}

## Матеріали
Поточна схема:
```proto
{{PROTO_CURRENT}}
```
Бажана зміна: {{DESIRED_CHANGE}}
Клієнти: {{CLIENT_LANDSCAPE}}
Обмеження розгортання: {{ROLLOUT_CONSTRAINTS}}

## Завдання
Знайди найбезпечніший шлях здійснити зміну.

## Що зробити
1. **Класифікація.** Чи зміна: сумісна на дроті; ламає згенерований код (джерела); ламає JSON/REST; ламає все. Аргументуй для кожного типу клієнтів.
2. **Сумісний шлях.** Якщо можливо, досягни мети лише додаванням: нове поле/метод, позначення старого застарілим, подвійний запис (старе й нове поле одночасно), зворотна сумісність значень.
3. **Якщо без поломки не обійтись.** Запропонуй нову версію пакета (`v2`), одночасну роботу `v1` та `v2`, план виведення `v1` з експлуатації (терміни, метрики використання, сповіщення).
4. **Порядок розгортання.** Хто першим — сервер чи клієнти — для додавання, видалення, зміни семантики. Як поводяться старі клієнти з новим сервером і навпаки (невідомі поля, нові значення enum).
5. **Захист номерів.** Що позначити як `reserved` (номери й імена).
6. **Збережені дані.** Якщо повідомлення зберігаються (черги, файли, кеш), як зміна вплине на них.
7. **Автоматизація.** Як налаштувати перевірку сумісності в CI і які правила (рівень суворості) обрати.
8. **Тести.** Тести сумісності: старий клієнт ↔ новий сервер, новий клієнт ↔ старий сервер; для JSON-клієнтів окремо.

## Формат відповіді
1. Припущення та питання (до 5).
2. Класифікація зміни (таблиця: тип клієнта → вплив).
3. Рекомендований план (кроки з порядком розгортання).
4. Змінений `.proto` (лише відмінності).
5. Тести та налаштування CI.
6. План відкату на кожному кроці.
7. Рішення, які ШІ не ухвалює сам (чи можна ламати клієнтів; терміни виведення старої версії; версіонування).

## Не роби
- Не перенумеровуй і не змінюй типи існуючих полів.
- Не пропонуй «оновити всіх клієнтів одночасно», якщо ви цього не контролюєте.
- Не вважай перейменування безпечним, не перевіривши JSON-клієнтів і згенерований код.
````

## Що перевірити людині

- [ ] Класифікацію підтверджено автоматичною перевіркою сумісності, а не лише міркуваннями ШІ.
- [ ] План має відкат для кожного кроку.
- [ ] Врахували збережені повідомлення та JSON-клієнтів.
- [ ] Порядок розгортання відповідає вашому процесу релізів.
- [ ] Видалені поля й імена позначено `reserved` (див. [A #5](A-pitfalls-catalog.md)).

## Типові помилки ШІ

- Пропонує «охайно» перенумерувати поля.
- Не бачить, що зміна режиму стрімінгу ламає всіх клієнтів.
- Забуває про JSON-клієнтів і збережені дані.
- Ігнорує порядок розгортання (сервер/клієнти).
- Радить видалити поле одразу замість поетапного виведення.
