# 03 · Створення .proto

> **Коли:** є затверджений дизайн (результат [02](02-service-design.md)) або чіткий список методів.
> **Результат:** `.proto`-файл за найкращими практиками, журнал рішень, таблиця номерів полів.
> **Далі:** обов'язково пропустіть результат через [04 · Рев'ю .proto](04-proto-review.md).

## Вхідні дані

| Плейсхолдер | Що підставити |
|---|---|
| `{{PROJECT_CONTEXT}}` | Блок з [00](00-project-context.md) |
| `{{RPC_TABLE}}` | Таблиця RPC з [02](02-service-design.md) або явний список методів із патерном кожного |
| `{{ENTITIES}}` | Сутності та їхні поля (назва, тип, обов'язковість, обмеження) |
| `{{HTTP_MAPPING}}` | Які RPC відкривати через REST і за якими URL (або «не потрібно») |

## Промпт

````markdown
Ти — експерт із Protocol Buffers і проєктування API.

{{PROJECT_CONTEXT}}

## Завдання
Напиши `.proto`-файл (proto3) для сервісу за наведеним дизайном.

RPC (перелічені явно, з патерном кожного):
{{RPC_TABLE}}

Сутності:
{{ENTITIES}}

HTTP-відображення (якщо потрібне): {{HTTP_MAPPING}}

## Вимоги до схеми
- `syntax = "proto3";`, пакет із версією (за контекстом), опції мови (`go_package`/`java_package` тощо) відповідно до контексту.
- Кожен RPC має власні `XxxRequest` та `XxxResponse`. Не використовуй доменну сутність як запит або відповідь напряму.
- Enum: перший елемент `<ENUM>_UNSPECIFIED = 0`; імена значень мають префікс імені enum.
- Номери полів 1–15 віддай найчастішим полям. Не пропускай номери без причини.
- Наявність поля: `optional` там, де треба відрізнити «не задано» від значення за замовчуванням. Часткове оновлення: `google.protobuf.FieldMask`.
- Час: `google.protobuf.Timestamp`; тривалість: `google.protobuf.Duration`; гроші: цілі одиниці або `google.type.Money`, не `float`.
- Ідентифікатори: `string`. Списки: `page_size`, `page_token`, відповідь із `next_page_token`.
- `oneof` — лише там, де взаємовиключні варіанти реальні; не використовуй `google.protobuf.Any` без потреби.
- Режим стрімінгу кожного RPC точно відповідає таблиці. Не додавай і не прибирай `stream` на власний розсуд.
- Кожен `service`, `rpc`, `message`, поле та значення enum має коментар (мова коментарів за контекстом), у якому описано семантику, обмеження й можливі коди помилок.
- HTTP-анотації додавай лише для RPC, які в HTTP-відображенні позначено як зовнішні. Для решти не додавай.
- Нічого зайвого поза описаним дизайном.

## Формат відповіді
1. Припущення та уточнювальні питання (якщо вони є; до 5).
2. Повний `.proto` в одному блоці коду.
3. Таблиця: `message | поле | номер | тип | примітка` (щоб зафіксувати нумерацію).
4. Журнал рішень: кожне нетривіальне рішення (чому `optional`, чому `oneof`, чому такий enum) одним реченням.
5. Рішення, які ШІ не ухвалює сам: де потрібне ваше підтвердження (нумерація, потреба стрімінгу, семантика пагінації).
6. Команди, якими перевірити результат (компіляція `.proto`, лінтер, перевірка сумісності) для інструментів із контексту.

## Не роби
- Не змінюй патерни викликів.
- Не вигадуй поля, яких немає в сутностях; сумніви виноси в питання.
- Не пиши реалізацію сервера чи клієнта.
````

## Що перевірити людині

- [ ] Режими `stream` збігаються з дизайном, нічого не додано і не прибрано.
- [ ] Нульові значення enum безпечні («невстановлено»), а не змістовні.
- [ ] Номери полів збережено в таблиці; ви розумієте, що вони ніколи не змінюватимуться.
- [ ] Типи грошей, часу, ідентифікаторів відповідають домену.
- [ ] Запустили компіляцію й лінтер (перелічені в п. 6 відповіді), а не покладались на слова ШІ.
- [ ] Результат пройшов [04](04-proto-review.md).

## Типові помилки ШІ

- Змішує ідіоми proto2 і proto3 або забуває `syntax`.
- Використовує сутність як запит/відповідь (немає місця для еволюції).
- Додає `stream` туди, де в таблиці unary (або навпаки).
- Пропускає нульове значення enum чи робить його змістовним.
- Дублює поля замість спільного message; або створює надто загальні `Any`/`Struct`.
- Додає HTTP-анотації всім методам, навіть внутрішнім.
