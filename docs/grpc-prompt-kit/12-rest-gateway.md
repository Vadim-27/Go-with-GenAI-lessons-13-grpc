# 12 · REST-місток (gateway / транскодинг)

> **Коли:** зовнішні клієнти (браузер, партнери, наявний фронтенд) мають звертатися до gRPC-сервісу як до звичайного HTTP API.
> **Результат:** обґрунтований вибір підходу, HTTP-анотації, конфігурація містка, таблиця відображення кодів, тести через `curl`.

## Що зробити
1. **Вибір підходу.** Порівняй для цього проєкту: генерований reverse-proxy (grpc-gateway), транскодинг на проксі (Envoy тощо), gRPC-Web, Connect-сумісні рішення. Коротко: коли що краще, обмеження (особливо стрімінг: клієнтський і двонапрямлений через HTTP/1.1-проксі зазвичай не підтримуються). Рекомендуй варіант.
2. **HTTP-анотації.** Додай до `.proto` лише для зовнішніх RPC. Дотримуйся правил відображення: параметри шляху, query-параметри для полів, що не в шляху, `body` для тіла. Методи: `GET` без тіла, `POST` створення, `PATCH` часткове оновлення.
3. **Формат JSON.** Імена полів (snake_case чи camelCase), вивід значень за замовчуванням, представлення enum і часу; узгодь з наявним REST.
4. **Помилки.** Таблиця «код gRPC → HTTP-статус» (використай стандартну відповідність; підтверди її для обраного містка) і формат тіла помилки.
5. **Автентифікація.** Як токен із `Authorization` потрапляє в metadata gRPC; де перевіряється; чи можна клієнту обійти місток і піти напряму.
6. **Стрімінг через міст.** Що доступно (наприклад, серверний стрімінг як потік JSON-рядків), що ні, і чому.
7. **Розгортання.** Окремий процес чи вбудований в сервіс; чому. З'єднання містка із сервісом: TLS/mTLS.
8. **Документація.** Якщо потрібно, генерація OpenAPI зі схеми.
9. **CORS і браузер** (якщо потрібні): дозволені джерела, заголовки.
10. **Тести.** Матриця запитів `curl` з очікуваними статусами: успіх, не знайдено, дубль, некоректний вхід, без токена, недостатня роль.

## Формат відповіді
1. Припущення та питання (до 5).
2. Порівняння підходів і рекомендація.
3. Змінений `.proto` (лише відмінності) та команди генерації.
4. Код/конфігурація містка.
5. Таблиця кодів gRPC → HTTP.
6. Матриця `curl`-тестів з очікуваними результатами.
7. Що перевірено запуском, а що ні.
8. Рішення, які ШІ не ухвалює сам (що публікувати зовні, формат JSON, де автентифікація).

## Не роби
- Не відкривай зовні RPC, які не позначено як зовнішні.
- Не обіцяй підтримку клієнтського/двонапрямленого стрімінгу через звичайний HTTP-міст.
- Не міняй семантику RPC заради зручності REST.

## Що перевірити людині

- [ ] Кожен `curl`-сценарій дає очікуваний HTTP-статус (запустіть, не вірте на слово).
- [ ] Відповідь через міст за змістом дорівнює відповіді нативного gRPC для того ж ресурсу.
- [ ] Внутрішні RPC не потрапили в зовнішню поверхню.
- [ ] Автентифікацію не можна обійти звертанням напряму до gRPC-порту ззовні.
- [ ] Формат JSON і помилок збігається з наявним REST (якщо потрібна сумісність).
- [ ] Внутрішні сервіси викликають gRPC напряму, не через міст (додатковий стрибок збільшує затримку).

## Типові помилки ШІ

- Анотує HTTP усі методи.
- Обіцяє двонапрямлений стрімінг через звичайний REST.
- Плутає camelCase і snake_case у JSON.
- Не передає заголовок автентифікації в metadata або ігнорує перевірку на межі.
- Неправильне відображення кодів помилок (наприклад, `AlreadyExists` у 400 замість 409).
