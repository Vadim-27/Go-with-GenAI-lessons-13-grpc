## Рівні тестів
1. **Юніт-тести домену** без gRPC: бізнес-правила, переходи станів, інваріанти.
2. **Тести обробників через справжній gRPC-транспорт у пам'яті** (клієнт ↔ сервер без мережі й портів), а не прямі виклики методів. Тоді перевіряються серіалізація, інтерсептори й коди статусу.
   - Табличні тести за таблицею помилок: для кожного рядка перевір **код статусу**, а не лише «є помилка».
   - Успішні шляхи й граничні значення (порожні рядки, нульові значення, великі повідомлення).
3. **Стрімінг** (для кожного стрімінгового RPC):
   - нормальне завершення (клієнт отримує `EOF`);
   - скасування клієнтом звільняє ресурси сервера (лічильник підписок/горутин повертається до нуля);
   - повільний споживач; обмеження;
   - збір результатів client-stream і підтвердження bidi;
   - запуск із детектором гонок.
4. **Безпека:** кожен рядок матриці негативних тестів, включно зі стрімінговими викликами.
5. **Контракт:** автоматична перевірка сумісності `.proto` з основною гілкою; golden-тест серіалізації для критичних повідомлень (необов'язково).
6. **Наскрізна перевірка (smoke):** скрипт, що запускає сервер (і міст, якщо є), проганяє ключові сценарії зовнішніми інструментами (`grpcurl`, `curl`) і зупиняє процеси.
7. **Автоматична перевірка витоків** горутин/ресурсів після тестів, якщо інструмент мови це підтримує.

## Вимоги до тестів
- Кожен тест перевіряє одну поведінку; назва описує очікування.
- Без «спання» для синхронізації там, де можна чекати на подію або використовувати опитування з таймаутом.
- Тест має **падати**, якщо прибрати ту поведінку, яку він перевіряє. Для критичних тестів (звільнення підписки, захист стріму) поясни, як ти в цьому переконався.
- Тести не залежать від порядку виконання й не діляться змінним станом.

## Формат відповіді
1. Припущення та питання (до 5).
2. План: таблиця `рівень | що перевіряється | чому важливо`.
3. Код тестів по файлах.
4. Команди запуску (звичайні, з детектором гонок, окремо стрімінг).
5. Мутаційна перевірка: які 3–5 навмисних поломок коду мають зробити тести червоними (і чи це так).
6. Що перевірено запуском, а що ні.
7. Рішення, які ШІ не ухвалює сам (що вважати достатнім покриттям ризиків; цільові тайм-аути).

## Не роби
- Не гонись за відсотком покриття заради нього.
- Не тестуй лише успішний шлях.
- Не пиши тести, що завжди проходять.
- Не змінюй код, що тестується, щоб тести проходили, без пояснення.

## Типові помилки ШІ

- Тестує методи напряму, оминаючи gRPC (інтерсептори й серіалізація не перевіряються).
- Перевіряє `err != nil`, але не код статусу.
- Тест скасування стріму не доводить звільнення ресурсів.
- Нестабільні тести через `sleep`.
- «Мутаційно сліпі» тести, які проходять навіть при зламаній логіці.
