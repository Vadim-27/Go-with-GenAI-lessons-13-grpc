# 07 · Реалізація клієнта

> **Коли:** сервіс потрібно викликати з іншого сервісу, CLI або тесту.
> **Результат:** надійна клієнтська обгортка з дедлайнами, ретраями лише для ідемпотентних викликів, мапінгом помилок і тестами.

## Вхідні дані

| Плейсхолдер | Що підставити |
|---|---|
| `{{PROJECT_CONTEXT}}` | Блок з [00](00-project-context.md) |
| `{{PROTO}}` | `.proto` цільового сервісу |
| `{{CLIENT_USE_CASES}}` | Для чого клієнт викликає сервіс; які методи потрібні |
| `{{IDEMPOTENT_METHODS}}` | Які RPC ідемпотентні (можна повторювати) |
| `{{TARGET}}` | Як клієнт знаходить сервер: адреса, DNS, балансування |

## Промпт

````markdown

{{PROJECT_CONTEXT}}

## Матеріали
`.proto`:
```proto
{{PROTO}}
```
Сценарії використання: {{CLIENT_USE_CASES}}
Ідемпотентні методи: {{IDEMPOTENT_METHODS}}

## Завдання
Напиши клієнтську обгортку над згенерованим клієнтом.

## Вимоги
- **З'єднання:** одне довгоживуче з'єднання на ціль; створюється один раз і закривається при завершенні. Не створювати з'єднання на кожен виклик. Використовуй актуальний рекомендований конструктор клієнта (перевір у документації; без застарілих блокуючих опцій).
- **Дедлайни:** кожен unary-виклик має таймаут (за політикою); для стрімів — окрема політика (загальний ліміт або heartbeat).
- **Ретраї:** лише для ідемпотентних методів і лише для кодів, які безпечно повторювати (`Unavailable`, за потреби `ResourceExhausted` із затримкою). Використовуй вбудований механізм конфігурації сервісу або ретрай-обгортку з експоненційною затримкою та джиттером. Загальна кількість спроб обмежена, сумарний час вкладається в дедлайн.
- **Неідемпотентні записи:** передавай ключ ідемпотентності, якщо сервер його підтримує; інакше не повторюй.
- **Помилки:** перетворюй gRPC-коди у типізовані помилки вашого домену (`NotFound` → «не знайдено» тощо), зберігаючи оригінал.
- **Автентифікація:** облікові дані per-RPC (токен у metadata); токен через TLS. Не логуй токен.
- **Балансування:** якщо цілей кілька або сервіс за балансувальником — налаштуй відповідно до контексту (клієнтське балансування через DNS або L7-проксі); поясни вибір.
- **Тестованість:** інтерфейс, який легко підмінити заглушкою; приклад тесту з фейковим сервером.
- **Стрімінг:** для стрімінгових методів — обробка `EOF`, скасування, повторне підключення з затримкою (для довгоживучих підписок).
- Метадані: передавай ідентифікатор запиту/кореляції, якщо це прийнято в проєкті.

## Формат відповіді
1. Припущення та питання (до 5).
2. Код клієнтської обгортки (повністю).
3. Конфігурація ретраїв/балансування (якщо використовується).
4. Приклад використання.
5. Приклад тесту із заглушкою.
6. Що перевірено запуском, а що ні.
7. Рішення, які ШІ не ухвалює сам (які методи насправді ідемпотентні, значення дедлайнів і ретраїв).

## Не роби
- Не ретрай неідемпотентні виклики.
- Не створюй з'єднання на кожен виклик.
- Не вимикай перевірку TLS, щоб «запрацювало».
- Не використовуй застарілі API.
````

## Що перевірити людині

- [ ] Усі виклики мають дедлайн; `grep` по викликах без таймауту (див. [A #11](A-pitfalls-catalog.md)).
- [ ] Список ідемпотентних методів підтверджено вами, а не вгадано ШІ (див. [A #12](A-pitfalls-catalog.md)).
- [ ] Ретраї обмежені за кількістю й часом; є затримка з джиттером.
- [ ] З'єднання створюється один раз і закривається.
- [ ] TLS-перевірку не вимкнено.
- [ ] Поведінка за падіння сервера перевірена вручну (зупиніть сервер і подивіться, що робить клієнт).

## Типові помилки ШІ

- Нескінченні ретраї без затримки; ретраї записів, що створюють дублі.
- З'єднання на кожен виклик.
- Відсутність дедлайнів.
- `InsecureSkipVerify`-подібні «швидкі рішення» для TLS.
- Застарілі конструктори та опції блокування.
