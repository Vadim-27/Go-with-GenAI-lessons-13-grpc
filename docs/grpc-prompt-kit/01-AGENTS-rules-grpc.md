# 01 · Постійні правила для ШІ (gRPC)

> **Як використати:** скопіюйте розділ «Правила» у `AGENTS.md`, `CLAUDE.md`, `.cursorrules` або системний промпт.
> Правила короткі й імперативні, щоб ШІ дотримувався їх без нагадувань. Адаптуйте під свій стек, але не послаблюйте пункти про безпеку та сумісність без причини.

## Правила

````markdown
# Правила для gRPC-коду в цьому репозиторії

## Контракт (.proto)
1. Спочатку `.proto`, потім код. Зміни схеми роби в `.proto` і перегенеровуй код. Згенеровані файли не редагуй вручну.
2. Пакет має версію (`company.service.v1`). Один сервіс на файл, чітка відповідальність.
3. Кожен RPC має власні `XxxRequest` і `XxxResponse`. Не використовуй доменну сутність як запит чи відповідь напряму.
4. Номер поля ніколи не змінюється й не використовується повторно. Видалене поле: `reserved` за номером і за іменем.
5. Перший елемент enum — `<ENUM>_UNSPECIFIED = 0` із безпечним значенням. Імена значень мають префікс імені enum.
6. Для наявності поля (відрізнити «0» від «не задано») використовуй `optional` або обгортки. Для часткового оновлення — `FieldMask`.
7. Час — `google.protobuf.Timestamp`, тривалість — `Duration`. Гроші — цілі одиниці або `google.type.Money`, ніколи `float`.
8. Списки мають пагінацію (`page_size`, `page_token`, `next_page_token`).
9. Кожен `service`, `rpc`, `message` і поле мають коментар.
10. Streaming — лише за конкретною потребою (живі оновлення, масове завантаження, двонапрямлена синхронізація). За замовчуванням unary.

## Сумісність
11. Додавати нові поля й методи можна. Видаляти, перейменовувати, змінювати тип чи номер, змінювати режим стрімінгу — не можна без нової версії пакета.
12. Перед завершенням змін запускай перевірку сумісності (`buf breaking` або еквівалент) і лінтер (`buf lint`).

## Помилки та дедлайни
13. Повертай помилки лише через gRPC-статус (`status.Error/Errorf` з `codes.*`). Не повертай «голі» помилки: клієнт побачить `Unknown`.
14. Не розкривай клієнту внутрішні деталі (SQL, стек, шляхи). Подробиці — у лог із ідентифікатором запиту.
15. Клієнт завжди задає дедлайн для unary-викликів. Сервер передає `ctx` далі й перевіряє його у довгих циклах.
16. Повторювати (retry) можна лише ідемпотентні виклики. Для неідемпотентних записів передбач ключ ідемпотентності.

## Стрімінг
17. У стрімінгових обробниках використовуй контекст потоку, а не фоновий контекст.
18. Конкурентний `Send` в один потік небезпечний: відправляє одна горутина/потік. Читання й запис можуть іти паралельно.
19. Кінець вхідного потоку (`EOF`) — штатне завершення, а не помилка.
20. Усе, що створює потік (підписки, горутини, таймери), має гарантовано звільнятися при виході з обробника. Для цього є тест на витік.

## Безпека
21. Без TLS у спільних і продакшен-середовищах не запускай. Відкритий текст — лише локально й з явним попередженням у логу.
22. Автентифікація та авторизація покривають І unary, І стрімінгові виклики. Політика доступу: заборонено за замовчуванням.
23. Токени передавай у metadata, не логуй їх. JWT перевіряй за бібліотекою: підпис, `exp`, `iss`, `aud`, дозволений алгоритм.
24. Не вмикай server reflection у продакшені без автентифікації.
25. Секрети й сертифікати не комітяться. Демо-секрети мають очевидно демонстраційні назви.

## Життєвий цикл і експлуатація
26. Сервер завершується м'яко з таймаутом (graceful stop), після якого зупиняється примусово (довгі стріми інакше блокують зупинку).
27. Є health-перевірка. Логи структуровані, без персональних даних. Інтерсептори: recovery, логування, метрики, автентифікація — окремими шарами.
28. Одне довгоживуче з'єднання на ціль, а не нове на кожен виклик. Враховуй, що L4-балансувальник «прив'язує» з'єднання до одного інстанса.

## Тести
29. Тестуй через справжній gRPC-транспорт у пам'яті, а не лише виклики методів напряму. Перевіряй коди помилок, а не лише успішний шлях.
30. Для кожного стрімінгового RPC: нормальне завершення, скасування клієнтом, витік ресурсів.
31. Для кожного механізму безпеки: негативні тести (немає сертифіката, чужий CA, протермінований токен, недостатня роль, стрімінговий виклик).

## Залежності та версії
32. Версії бібліотек і плагінів фіксуй. Версія плагіна кодогенерації має відповідати версії runtime-бібліотеки.
33. Не використовуй застарілі API. Актуальність API перевіряй за офіційною документацією, а не за пам'яттю.

## Поведінка при відповіді
34. Якщо даних бракує, постав до 5 уточнювальних питань. Припущення виписуй окремо.
35. Не вигадуй API бібліотек. Якщо не впевнений — скажи й перевір документацію.
36. Не стверджуй «працює» без запуску. Явно розділяй: перевірено запуском / не перевірено.
37. Рішення, що належать людині (стратегія нумерації полів, потреба стрімінгу, відповідність кодів помилок реальним збоям, вплив зміни на наявних клієнтів), лише пропонуй із обґрунтуванням, не ухвалюй мовчки.
````

## Примітки

- Правила 1–12 найкорисніші для `.proto`-рев'ю; 13–20 — для реалізації; 21–25 — для безпеки. Якщо в команді різні агенти для різних задач, можна розділити.
- Пункти 21 і 24 спрощено для локальної розробки: демо-режим з відкритим текстом припустимий, якщо він явно ввімкнений прапорцем і позначений у логу.
- Пункт 28 стосується Kubernetes: звичайний сервіс типу ClusterIP балансує на рівні з'єднань, тож довгі gRPC-з'єднання можуть залишитися на одному поді. Докладніше — в [15](15-production-hardening.md).
