# 04 · Рев'ю .proto

> **Коли:** після створення `.proto` ШІ чи людиною; перед злиттям будь-якої зміни схеми; при аудиті успадкованого контракту.
> **Результат:** перелік проблем із пріоритетами та вердикт щодо сумісності.
> Це найважливіший промпт набору: помилки в `.proto` найдорожчі, бо вони потрапляють на дріт і в клієнтів.

## Що перевірити
### 1. Сумісність (якщо є попередня схема)
- Змінені чи повторно використані номери полів; змінені типи; видалені поля без `reserved`.
- Перейменування (безпечне для бінарного формату, але ламає згенерований код і JSON).
- Зміни enum (видалення значень, зміна нульового значення).
- Зміна режиму стрімінгу RPC; видалені або перейменовані методи; зміна пакета чи імені сервісу.
- Переміщення полів у/з `oneof`; зміна `optional`.
Класифікуй кожну зміну: сумісна на дроті / ламає джерела / ламає JSON / ламає все.

### 2. Дизайн
- Власні Request/Response для кожного RPC. Доменна сутність як запит чи відповідь — зауваження.
- Enum: `UNSPECIFIED = 0`, префікси значень.
- Пагінація списків, часткове оновлення, ідемпотентність записів.
- Типи: час, тривалість, гроші, ідентифікатори.
- Використання `Any`, `oneof`, вкладених типів, `map`.
- Стрімінг лише там, де це виправдано.
- Коментарі до всіх елементів; конвенції іменування (PascalCase для message/service, snake_case для полів, дієслова для методів).

### 3. Безпека та експлуатація
- Чи можуть повідомлення стати завеликими (необмежені `repeated`, `bytes`)?
- Чи є поля з чутливими даними, які не повинні потрапити в лог?
- Чи зрозумілі коди помилок для кожного RPC?

## Формат відповіді
1. **Вердикт щодо сумісності:** `сумісна` / `ламає джерела` / `ламає дріт` / `нова схема (не застосовно)` та обґрунтування.
2. **Таблиця знахідок:** `# | рівень (Блокер / Серйозне / Мінор) | місце (message.поле / rpc) | проблема | чому це важливо | пропонована правка`.
3. **Виправлений фрагмент** `.proto` лише для блокерів і серйозних проблем.
4. **Рішення, які ШІ не ухвалює сам:** де потрібне ваше рішення (наприклад, чи можна ламати клієнтів).
5. **Команди перевірки:** лінтер і перевірка сумісності з основною гілкою для інструментів із контексту.

## Не роби
- Не хвали схему замість пошуку проблем. Якщо знахідок немає, так і скажи, і назви, що саме перевірено.
- Не пропонуй перенумерувати поля вже існуючої схеми.
- Не вигадуй проблем, яких немає.

## Що перевірити людині

- [ ] Усі блокери виправлено або свідомо прийнято (з записом, чому).
- [ ] Вердикт про сумісність підтверджено автоматичною перевіркою (`buf breaking` або еквівалент), а не лише словами ШІ.
- [ ] Для змін, що ламають клієнтів, є план міграції ([16](16-schema-evolution.md)).
- [ ] Якщо є REST/JSON-клієнти, перейменування полів розглянуто окремо.

## Типові помилки ШІ

- Рецензент погоджується з усім («схема виглядає добре»). Явно вимагайте шукати проблеми.
- Не помічає зміну режиму стрімінгу або видалення значення enum.
- Вважає перейменування поля безпечним, забуваючи про JSON і згенерований код.
- Пропонує «охайно перенумерувати поля» — найгірша порада для схеми в експлуатації.
